## 二、实测发现(按严重度)

### F1 冷加载布局位移 CLS 0.24-0.34(严重,CWV「差」)

- 实测:文章详情页(4/4 篇未访问过的文章)冷加载 CLS **0.3389**@~350ms,标签页 0.2424、
  分类页 0.3389、留言板(54 条留言)0.2722;位移源全部是 `FOOTER.border-t` 被顶下去。
- 机制(源码):`apps/web/src/app/(public)/loading.tsx` 的路由级骨架只有"3 张卡片"的高度
  (约 500px)。这些路由是动态渲染 + 流式 SSR,首屏先画骨架,真实内容到达后替换,
  正文实际高度 3000-8000px,页脚被瞬间推下。（该全局骨架已在 2026-09 优化中移除，
  改为让详情/归档路由等待数据后整页提交，以恢复真实的 404 状态码。）
  <!-- check-docs:allow-missing-path -->
- 对照组:**同一篇文章在 ISR 缓存热了之后 CLS = 0.0000**(整页 HTML 一次性到达,骨架不可见)。
- 影响:每次部署后的首个访客、每个 revalidate 窗口(60s)后的第一个真实用户和爬虫,
  都会经历一次「差」级 CLS。对以 SEO 为明确目标的博客,这是当前最值得修的前端缺陷。
- 修复方向:骨架高度贴近真实内容(文章页骨架至少预留首屏阅读列高度),或文章页放弃流式骨架
  改为整页等待;留言板需要按页大小预留列表高度——第一轮的「0.273→0.004」修复只在小数据量下成立。

### F2 头部导航文字压在壁纸上对比度 2.68-3.0:1(中等,AA 不合格)

- 实测:像素级采样(去除文字像素后取背景亮度,与计算色算 WCAG 比值),首页透明头部导航链接
  中位 **3.0:1**、最差 **2.68:1**,要求 4.5:1。hero 文案本体已达标(kicker/desc/h1 全部
  4.79-5.11:1,第一轮的修复有效)。
- 机制(源码):`header[data-over-hero] .nav-link { color: rgb(255 255 255 / 0.92) }` ——
  0.92 半透明白叠在**亮度不可控的壁纸上**,数学上就不可能保证 AA。axe 对这些节点只能报
  `color-contrast` incomplete(背景是图片),所以「axe 零违规」依旧不覆盖它。
- 修复方向:去掉透明度(`#fff` + 既有 text-shadow),或给头部加一层随滚动增强的实底;
  把头部的对比度纳入像素级回归脚本。

### F3 文章页冷缓存水合失配 React #418(中等,自恢复)

- 实测:清缓存冷加载文章详情页,**5/5** 次复现 `Minified React error #418`
  (水合失配);缓存热后 0/1 复现。首页/列表/留言板/登录均未复现。
- 机制(推断,源码):文章页是流式 Suspense 边界(SSR 首屏为 `<!--$?-->` 骨架),
  chunk 加载慢时边界已在水合前解析,与客户端重放发生竞态;React 用客户端重渲染自愈,
  代价是整棵文章树重渲染(移动端慢网络下浪费更明显)。
- 影响:功能无损、用户无感,但属于每次冷加载都可能触发的多余渲染;建议升级关注
  Next.js/React 相关 issue,或让正文边界在水合后再解析。

### F4 页脚标题层级跳级(轻微)

- 实测:axe `heading-order`(moderate)在 /about、/now、/login、/register、404 各报 1 节点:
  主内容 `h1` 之后直接是页脚的 `h3`(「浏览」「订阅与本站」)。/messages 因先出现 `h2` 而合规。
- 修复方向:页脚分组标题改 `h2`,或改为非标题元素+样式。第一轮把「页脚 h2 在 h1 前」修成了
  「h3 跟在 h1 后」,跳级问题换了形态残留。

### F5 遗留小项(轻微)

- `SiteIcons.tsx` 鱼形 SVG 的腮红仍是旧令牌 `#f472b6`(当前 `--primary` 为 `#ef5f7a`),
  另有两处 `#1e293b` —— globals.css 之外仅剩这 3 处硬编码色。
- /articles 首载触发 **41 个 RSC 预取请求(52KB)**:Next 对视口内 `<Link>` 的默认行为,
  列表越长预取越多;是设计取舍而非缺陷,但 72 篇/页的列表页上值得用 `prefetch={false}`
  收敛分页区链接。
- 首页冷载总量 1.32MB(其中壁纸图片 727KB、JS 传输 310KB/18 chunk、RSC 31KB):沉浸式
  hero 的合理代价,图片已是响应式变体;列表页 JS 传输 310-314KB,与首页持平,无明显路由级差异。

### F6 `/archive` 是构建期静态预渲染,空状态会被永久烤进产物(截图复核时发现,中等)

- 【历史记录,页面已变更】实测(2026-09-18):当时的归档页(旧路径 `(public)/archive`,
  已被 `/projects` 取代)长时间渲染「还没有发布文章,敬请期待」——构建阶段 API 尚未启动,
  空数据被烤进静态产物;该页没有 `revalidate`/`dynamic` 导出(全站只有首页有 `revalidate = 60`),
  因此不像首页那样能自愈。
- 推论(生产):`npm run update` 构建时旧 API 仍在线,所以该页烤入的是**构建时刻**的数据;
  两次部署之间新发布的文章不会出现,直到下一次重新构建。
- 修复方向(当时已落地):数据页统一 `export const revalidate`;部署文档写明
  「构建必须能访问 API」。本文 C 维度中 archive 的 LCP/CLS 实测值来自那个时代的空页面,仅作参考。

## 三、实测确认的强项

- **响应式与排版零缺陷(实测)**:6 档宽度(320/390/768/1024/1280/1440)× 明暗两主题 ×
  10 个路由 = 120 次加载,**零横向溢出、零 <12.5px 界面文字**。
- **键盘可达性满分(实测)**:首页/列表/文章/留言板/登录各真实 Tab 30 步,全部可聚焦元素
  (含登录页 29 步)**100% 有可见焦点指示**。
- **暗色主题 axe 干净(实测)**:`.dark` 切换稳定后,违规仅剩 F4 的 heading-order。
  (注意:切换后立即跑 axe 会报大量 `color-contrast` serious——那是采样到主题过渡动画中间态的
  测量假象,等过渡结束即消失。这也提醒:「axe 零违规」类结论必须写明采样时机。)
- **交互功能 11/11 通过(实测)**:主题切换、移动菜单、目录高亮、移动目录抽屉、代码复制、
  图片灯箱、首页搜索、留言表单、音乐播放器面板、特效残留检查、回到顶部。
  其中两项在测量中曾显示失败,均为测量环境问题而非产品缺陷:
  音乐面板失败 = 并发构建损坏了被测实例的 chunk(清目录重建后通过);
  主题切换失败 = 浏览器 profile 残留了上次的 `theme=dark`,断言要求从亮色开始。
- **第一轮的两项前端修复持续有效(实测)**:hero 文案像素对比度 4.79-5.11:1(修复前 1.6-2.4);
  页脚 RSS/sitemap 零预取(此前每页 ~64KB 无效传输,本轮全部 8 条路由 feed 请求数 = 0)。
- **未提交的管理员登录修复有效(实测)**:输错密码正确显示「用户名或密码错误」——修复前该
  场景会因 Response body 重复消费抛 TypeError 而误报「网络错误」。
- **字体与缓存策略(沿用)**:零字体请求、系统字体栈、`/_next/static` immutable 缓存,本轮无改动。

## 六、修复优先级建议

1. **F1 骨架高度**(最大 CWV 收益):文章页骨架贴近首屏真实高度;留言板按页大小预留。
2. **F2 头部导航不透明白**:一行 CSS;把头部+hero 的像素对比度纳入冒烟断言防回退。
3. **F4 页脚 h3 → h2 或非标题**:5 个路由的 axe moderate 清零。
4. **门禁恢复**:修掉 `error-envelope.test.ts` 的 2 个类型错误(后端文件,但门禁是共享的)。
5. F3 观察 Next.js 上游;F5 顺手清理。
